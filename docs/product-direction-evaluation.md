# 个人经验型桌面 AI 助手：产品方向评估

研究日期：2026-09-21。状态：研究建议与待验证假设，尚非已确认产品决策。

依据：已完整读取《产品方向对话记录_2026-09-20.md》以及“ 双向论证产品方向 ”引用对话；外部材料以本次读取的官方产品说明、原始论文与研究机构页面为主。产品官网只能支持其公开定位和功能主张，不证明实际质量、留存或商业成功。本轮未进行竞品实机横评，也未实施产品功能或启动用户实验。

## 1. 目前最值得下注的判断

“个人档案馆／图书馆／博物馆”比农场更适合表达 AI 协作形成的长期资产，但尚无依据证明它更能让用户持续使用或付费。建议把它定义为：**一个随手可用的桌面 AI 助手，能够把共同解决问题的经验转变为以后可调用、可纠正、有来源的个人工作记忆。**

用户可以理解为：“少解释一次背景，少重做一次研究，少踩一次已经踩过的坑。”个人空间让这些积累可见、有归属感；它是否需要成为主要界面，应独立验证。

这次转向改变的是“积累什么”：从与工作成果间接关联的虚拟资产，转为与用户经历直接关联的案例、决策、方法与作品。它并不自动解决“为什么今天要打开”“为什么要相信”“为什么为它付费”。

建议保留原方案中的三个约束：在当前注意力位置召唤和交付；使用成熟模型与 Agent 运行框架；默认不要求用户逐次验收或维护笔记。共视角能力可以跨应用，首批用户和验证任务仍需聚焦。架构通用并不意味着第一版覆盖所有场景。

原讨论里“农场的等待适合异步 Agent”仍有解释力，但不能推出“长期经验必须来自异步任务”。即时问答只要产生可复用判断，也能贡献经验。异步任务的进度表达与经验的长期组织，是两项可以独立排期的能力。

## 2. 双向钢人：分别把两种方向的最强版本说清楚

### 支持个人空间的最强论证

第一，积累物与真实价值同源。一次比较工具的讨论，可以留下选择依据；一次排障可以留下条件和反例；一次方案交付可以留下可复用材料。下一次任务使用这些内容，能够产生真实收益。农场的作物大多表达“做过多少”，经验对象有机会改变“以后怎么做”。

第二，它可以承载模型本身不具备的个人历史。公共知识可以重新搜索，但某个项目为什么放弃过方案、某条规则在哪个条件下失效、用户为何修改过结果，未必能从互联网重新获得。前提是这些经验足够准确、可以迁移，并且确实被调用。

第三，成长可以具体可查。用户看到的不必是“你的 AI 升到 12 级”，可以是“这份评审框架已经在三个不同项目里使用，其中一个项目发现了边界”。它既表达积累，也容纳修正，不必把失败从世界中抹掉。

第四，个人空间能够同时服务工作和自我理解。一次重要判断可以在档案视图中追溯证据，在方法视图中复用，在回顾视图中展示变化。收藏物的意义来自真实经历，而非额外游戏任务。

### 反对个人空间的最强论证

第一，语义契合并不等于需求强烈。多数即时问题在解决之后就结束了，普通知识可以再次生成。用户也可能更喜欢每次从最新材料重新判断。若跨任务复用稀少，自动沉淀只是低成本制造冗余。

第二，自动化可能削弱参与感。亲手整理、命名、摆放和选择本来就可能是收藏乐趣的一部分。AI 替用户完成全部策展后，用户未必把它当作自己的世界；但把这些工作交还用户，又可能重演知识管理的维护负担。

第三，工作记录可能增加压力。空间若充满未完成事项、失败和效率数字，用户可能不愿进入。博物馆式陈列也可能把暂时判断塑造成“我就是这样的人”，加重对旧经验的依赖。

第四，信任难度高于普通收藏。错归属的人物、缺失的前提、被误记成事实的 AI 建议，都会污染后续任务。积累越多，并不保证答案越好；错误也可以累积。

第五，竞争已十分接近。AI 记忆、自动组织、知识图谱、任务执行和桌面入口都已有产品组合。新产品需要证明更好的任务效果或更好的使用体验，而不能依赖“别人只有聊天，我们有记忆”的叙事。

### 农场和桌宠仍然拥有的优势

农场让回访理由直观、轻松，开始使用当天就能提供可见进展；桌宠则可以提供陪伴、入口识别和明确状态。这些价值不依赖历史资料质量，也不要求用户对知识积累感兴趣。对以娱乐和陪伴为主要动机的人，它们可能优于个人档案馆。

针对《Neko Atsume》的研究调查了 1,972 名玩家，并提出用习惯理解这种短时、反复的参与方式；它没有证明这种效果可以迁移到工作助手，更没有证明“成瘾性”是适当的产品目标。[原始论文](https://www.sciencedirect.com/science/article/pii/S1071581918305251)

2024 年游戏化元分析覆盖 35 项干预、约 2,500 名参与者，观察到对内在动机较小的总体正效应；研究处于教育情境，不能直接用作桌面 AI 留存预测。[原始研究](https://doi.org/10.1007/s11423-023-10337-7)

| 判断维度 | 农场／桌宠 | 个人经验空间 |
|---|---|---|
| 首日可理解的奖励 | 通常更容易呈现 | 需要先有一段有意义的经历 |
| 异步状态和等待 | 映射直观 | 需要单独的任务状态设计 |
| 工作资产的复用 | 通常间接 | 可以直接参与下一次任务 |
| 情感价值 | 陪伴、趣味、惊喜 | 归属、成就、回忆、自我理解 |
| 维护风险 | 养成压力、装饰负担 | 校正、组织、错误积累 |
| 最关键的待证点 | 趣味能否持续帮助真实使用 | 经验能否有效复用且值得信任 |

本表是设计判断，不是对照实验结论。推荐以经验空间承载长期资产，允许桌面入口保留光点或角色；先分别验证，不把农场、宠物、档案馆全部堆进第一版。

## 3. 它到底是什么产品

核心工作单位建议为“问题案例”，而不是聊天或笔记。一份案例描述：当时想解决什么、约束是什么、看到了哪些证据、尝试过什么、最后采取了什么、结果如何、哪些内容可能复用。

一次对话可能包含几个案例；一个案例也可能跨越多轮对话、多天和多个应用。案例可以尚未解决，结果可以未知。完成回答不能自动等同于完成任务。

这里有三个不同的产品承诺：

1. 当下：理解当前授权上下文，迅速提供可用帮助。
2. 跨任务：带回相关旧经验，说明适用条件，减少重新解释和重做。
3. 长期：让用户查看、修订和回顾自己积累的经验与作品。

最有辨识度的瞬间是：用户正在做一个新任务，助手提出“上次采用过这个方法，但它依赖一个这次不成立的条件，因此建议调整”，并展示可核查的依据。只有“我记得你以前说过……”还不够。

与普通知识管理的区别，应体现在默认行为和评价标准上：材料从真实任务中产生；记忆会进入未来任务；结果与纠正会更新记忆；最终评价当前工作是否改善。一个做得很好的知识管理产品同样能实现这些行为，因此这是竞争方向，不是天然独占的新品类。

也应正视一个强基线：现有桌面助手读取一个开放的本地知识库，就可能满足相当多需求。若增加的新系统没有明显降低摩擦或提高效果，产品更适合成为插件或体验层，而不是要求用户迁移到完整新平台。

## 4. 现有方向对比：哪些已是共识，哪些仍有机会

观察口径为 2026-09-21 官方公开说明；没有写出的能力不等于竞品一定没有。表中“可争取的差异”均需实际横评。

| 方向与代表 | 已有价值／公开能力 | 对本方向的约束与启发 |
|---|---|---|
| Second Brain（第二大脑）／CODE 方法 | 捕获、组织、提炼、表达，本身就强调形成现实成果 | 不能把它简化为囤积笔记；机会是减少维护并把复用放进当前任务。[Forte Labs](https://fortelabs.com/blog/basboverview/) |
| 对象型 PKM（个人知识管理）／Capacities | 以人物、书籍、项目等对象及关系组织内容 | 对象模型和关系图已非差异点；需要验证任务案例、结果反馈和时间演变的价值。[Capacities](https://capacities.io/) |
| AI 收藏／mymind | AI 辅助理解和找回收藏，视觉组织降低手动分类负担 | 可借鉴低维护和视觉归属感；仅自动标签与收藏墙不构成新产品。[mymind](https://mymind.com/what) |
| 个人回忆／Day One | “On This Day”按日期带回个人记录 | 证明一种产品回顾机制已经存在，不证明我们的用户愿意回顾工作；可增加“当前项目相关”的召回条件。[Day One](https://dayoneapp.com/features/on-this-day/) |
| Lifelogging（生活记录）／MyLifeBits、Windows Recall | 前者探索个人数字档案，后者以屏幕快照帮助找回看过的信息 | 找回经历与理解其意义不同；可以保留来源线索，没必要先实现全量记录。[MyLifeBits](https://www.microsoft.com/en-us/research/project/mylifebits/)、[Recall](https://support.microsoft.com/en-us/windows/privacy/privacy-and-control-over-your-recall-experience) |
| 对话记忆／Claude | 工作背景记忆、可编辑摘要、项目边界和无痕对话 | “它记得我”与“记忆可编辑”已是基线；需证明更细的案例及其结果有增量。[官方说明](https://claude.com/blog/memory) |
| AI 记忆基础设施／Mem0 | 为 Agent 存储与检索跨会话偏好、事件等信息 | 可提供底层能力；用户价值仍取决于何时存、怎么更新、如何正确参与任务。[官方介绍](https://mem0.ai/blog/introducing-mem0) |
| 系统入口／Raycast | 当前窗口上下文、跨会话记忆、项目和自动化 | 快捷召唤加记忆已存在；要测交付位置和复用质量，不能只比入口形状。[官方手册](https://manual.raycast.com/ai/ai-chat) |
| 记忆与行动结合／Mem | Workspace 与 Agent 结合，维护人物、项目、决策等上下文并主动协助 | 属于直接竞争者，已很接近“可见记忆反哺工作”的叙事。[Mem](https://get.mem.ai/) |
| 本地工作助手／Rowboat | 将邮件、会议和助手对话组织为双链知识图谱，并支持后台任务等工作面 | “本地＋知识图谱＋Agent”也已被直接覆盖；需比较具体案例复用和就地交付体验。[官方仓库](https://github.com/rowboatlabs/rowboat) |

本轮没有找到足够证据，把“个人博物馆”认定为已成立且独立的商业品类。更可靠的理解是：它与视觉收藏、日记回顾和个人数字档案有交集，能够提供一种交互与品牌隐喻。

值得尝试的差异组合是：低打扰的就地协助、完整的问题案例、带条件的经验复用、跨工具且可迁移的资产、用户能理解的成长表达。任何单项都容易重叠，组合也需要用效果证明。

这不构成数据网络效应：一个人积累的经验不会自然改善所有人的产品。它最多首先形成个人累积价值。真正可长期积累的优势可能来自特定工作流的经验质量、纠错机制和获得用户信任的交互，而非资料总量。

## 5. 核心循环：在当前任务里完成价值兑现

当前授权上下文 → 就地协助 → 形成问题案例 → 后台提取候选经验 → 组织、去重与关联 → 新任务中检索并核对适用条件 → 生成可用结果 → 记录采用、纠正或反例。

| 环节 | 用户可感知的行为 | 系统应保留的关键边界 |
|---|---|---|
| 召唤 | 在当前应用按键、说话或选中内容 | 采集范围可见；调用时读取不等于全天监控 |
| 帮助 | 原处出现短答或结果，复杂内容可展开 | 回答不能被强迫导流到“馆内”；长任务另有清晰状态 |
| 沉淀 | 任务后可选提示“留下一条经验”，无需打分 | 默认先是候选；没有结果证据就标记未知 |
| 组织 | 自动归到相关项目，用户可以纠正 | 相似内容不必合并；相关不等于因果 |
| 召回 | 在新任务中带回少量相关材料和理由 | 权限、项目、版本、时间和适用条件先过滤 |
| 使用 | 直接带入草稿、解释、比较或行动建议 | 清楚区分引用旧材料与形成新判断 |
| 更新 | 新结果让旧经验补充边界或失效 | 保留变化原因；错误不能因被反复总结而“坐实” |

默认情况下后台可完成抽取、归类和低风险索引。事实冲突、归属不明和高影响规则才进入需要注意的队列；用户未确认的内容可以继续作为有标签的线索，但不静默升级为确定事实。

以一次功能方案评审为例：用户上次因为依赖尚未提供而选择简化方案，后来记录上线结果。数周后另一个项目出现类似选项，助手找到旧案例，并指出原来的依赖限制已经变化，因此旧方案只能作为参考。用户采用新选择后，两次经历共同构成一个有适用边界的方法。个人空间可以展示“判断如何改变”，而不是只陈列两个最终答案。

冷启动应利用用户明确选择的一个已有项目和少量真实案例。第一天就能展示证据清楚的回顾，随后等待自然出现的复用机会；没有历史时，承认记忆尚未积累，用即时帮助建立价值，不能伪造“已经很懂你”。

日常档案沉淀、方法提炼与主动干预采用不同门槛：保存一条带来源的候选可以便宜；把一次经验提升为通用方法需要更多依据；主动改变执行或对外行动需要现有授权，记忆本身不能给予权限。

## 6. 隐喻与命名

| 隐喻 | 最适合的内容和感受 | 主要问题 | 建议角色 |
|---|---|---|---|
| 档案馆 | 来源、时间、版本、决策经过 | 容易显得冷、被动、陈旧 | 事实和历史的底层承诺 |
| 图书馆 | 方法、案例、可借用材料 | 容易让人以为要整理分类或阅读长文 | 方法与复用视图 |
| 博物馆 | 有意义的作品、关键转折、成长故事 | 策展负担；可能只值得偶尔来一次 | 项目结束、阶段回顾和精选展示 |
| 记忆宫殿 | 熟悉的位置、空间联想、个人摆放 | 空间导航和学习成本；自动重排破坏位置线索 | 给有明确需求的人提供可选布局 |
| 个人世界 | 陪伴、探索、归属、持续变化 | 承诺过大，容易滑向复杂游戏系统 | 后续品牌想象与个性表达 |
| 工作室／书房 | 当前工作与历史积累并存 | 隐喻相对常见 | 优先测试的外层名称与整体体验 |

若必须选一个数据组织隐喻，我选择“档案馆”；若必须选一个面向用户的空间，我优先测试“书房／工作室”；“博物馆”更适合精选回顾。三者是同一批对象的不同用途，不需要创建三套库。

“AI 是馆员”可以解释整理与找回；日常它还需要是执行当前任务的助手。用户不应被迫扮演馆长，每天审批所有藏品。

命名可分为三条候选方向：

- 功能理解：回用、经验簿。容易指向复用，但情感较弱。
- 长期陪伴：常在、伴知。能表达持续存在，但功能需要副标题解释。
- 空间归属：知舍、我的书房。适合温和的个人空间，也最容易被误解为笔记软件。

这些只是命名草案，未做商标、域名或重名可用性核验。建议先用同一个原型做五秒理解测试：用户看名字和一句话后，能否说出“帮我做事、记住经验、以后再用”，以及是否误以为需要手动记笔记。内部工作名可暂用“个人经验型桌面助手”，无需现在确定品牌。

## 7. 信息架构与对象模型

前台建议只有四个主要入口：当前任务、项目、经验、回顾。来源和记忆管理可以从对象详情进入；人物、时间线、技能和偏好是关联视图，不必各占一个一级导航。默认打开当前任务，回顾空间按需进入。

数据分为来源、经历、提炼和呈现四层。来源是证据；经历记录发生了什么；提炼记录可复用内容与适用范围；呈现是对这些对象的编排。不能让一张生成式“展品说明”覆盖底层事实。

| 对象 | 最小字段／含义 | 关键关系和限制 |
|---|---|---|
| 来源 Source | 地址或文件标识、版本、片段定位、时间、权限、作者／发言者 | 支持某个主张；被读取不等于被用户认可 |
| 事件 Event | 发生时间、记录时间、行为者、行为、对象 | 发起／修改／验证一个案例；发生时间不能用同步时间代替 |
| 问题案例 Case | 问题、目标、约束、状态、项目、相关事件 | 包含多个答案和尝试；跨会话持续 |
| 答案／尝试 Attempt | 建议内容、方法、输入、执行情况 | 响应问题；AI 建议、用户选择与执行分开 |
| 结果 Outcome | 完成证据、用户报告、观察指标、已知局限 | 评价一次尝试；允许未知、失败、部分有效 |
| 决策 Decision | 候选项、选择、理由、决策者、生效范围、时间 | 基于来源和约束；由后续决定替代而非被静默改写 |
| 知识／经验 Claim | 结论、证据状态、适用条件、反例、复核时间 | 从案例提炼；支持／反驳其他主张 |
| 方法／技能 Procedure | 触发条件、输入、步骤、验收方式、工具和权限 | 用于未来任务；可执行技能必须另有验证与授权 |
| 人物 Person | 身份标识、别名、所属项目、角色 | 谁说／决定／参与；同名不可直接合并 |
| 项目 Project | 目标、范围、当前状态、访问边界 | 容纳案例、人物和局部记忆；项目结束不等于所有方法过期 |
| 偏好 Preference | 内容、适用场景、来源、显式或推断、有效期 | 影响表达或选择；一次行为不能直接固化成全局偏好 |
| 展品／专题 Exhibit | 引用对象、编排方式、用户选择、叙述 | 是视图；删除展品不默认删除事实，删除事实则必须更新展品 |

时间线是事件的视图；答案是一次候选输出；知识是带依据和边界的主张；技能是可复用步骤。这些对象不应全部压成一类笔记，也不必一开始都做成独立复杂页面。

核心关系可表达为：项目包含案例；案例由事件推进；尝试回应问题并产生结果；决策选择方案；来源支持或反驳主张；方法在新案例中被使用；结果修订方法；展品引用这些变化。关系边本身也要记录证据、时间和推断状态。

所有长期对象至少需要稳定标识、来源、范围／权限、发生与记录时间、版本、状态、替代关系和保留策略。证据状态优先用明确类别：原文记录、用户明确决定、工具结果、推断、待核实；避免用未经校准的置信度百分比制造精确感。

还需分别记录“用户分享过”“AI 检索到”“内容曾显示在屏幕上”“用户明确认可”。系统无法因为某段内容出现在窗口中，就声称用户读过、理解或同意了它。

典型生命周期：候选 → 带来源的记录 → 经验证或经明确采用的经验 → 被补充／被替代／失效；任何阶段都可纠正或删除。旧决策可能已经不适用于当前任务，但仍然适合回答“当时为什么这样做”。

实现上，第一版可以使用结构化存储维护状态和关系，以 Markdown 保存可读内容，并使检索索引可以重建。图数据库、三维空间与复杂路由都不是验证闭环的前提。若接入已有 Obsidian，要约定唯一事实源和写入边界，避免出现两套互相总结、反复覆盖的记忆。

## 8. 长期留存、复盘与个性化

建议区分三种回访动机：有当前问题所以召唤；遇到相似任务所以复用；想理解自己的积累所以回顾。第一种支撑即时价值，第二种证明记忆收益，第三种验证个人空间。三者的频率可以不同，博物馆每月有价值并不意味着每天应该推用户去逛。

真正有用的复盘应回答“什么判断改变了、哪种方法可再用、什么条件导致失败、什么问题仍未解决”。只有任务数量、工作时长或漂亮成长叙事，很容易制造进步错觉。对于情感回忆，则应由用户选择是否展示，不将所有经历按生产力价值排序。

自动保存不等于用户已经学会。如果产品声称帮助人的能力成长，就需要观察人在新情境中的判断与迁移；如果只是 AI 更容易找到历史材料，应如实称为检索和任务帮助。两种价值都可以成立，但不能混为一谈。

个性化分层：表达偏好、项目上下文、经过多次检验的方法、长期目标。不同层的证据和授权要求不同。推荐保留“本次忽略历史”“重新从证据判断”和“这不代表我的长期偏好”等入口，防止用户被过去的记录束缚。

已有偏好只能提供上下文，不应使助手自动赞同旧判断；历史经验既可提供答案，也可提示哪里不适用。跨项目泛化尤其要检查约束。新工具版本、人员变化或目标改变，都可能使旧经验失效。

## 9. 信任风险会直接决定用户愿不愿意把它放在桌面上

| 风险 | 产品层应有的处理 |
|---|---|
| 把全天看过的东西永久收走 | 从明确召唤与指定来源开始；会话内可见采集状态，支持暂停和排除应用 |
| 本地存储被误解为不会上传 | 分别说明存储、索引、抽取、回答和同步在哪里发生；云端模型实际会收到哪些片段 |
| AI 猜测变成个人事实 | 保留原始出处与发言者；推断始终可识别，用户可以直接纠正 |
| 私人、公司、客户材料串用 | 按项目、身份、来源权限隔离，检索过滤在调用前完成 |
| 删除页面但派生记忆还在 | 删除覆盖摘要、关系、索引、缓存及展品引用；说明备份保留与清除边界 |
| 历史材料中的指令污染后续行为 | 把来源当作数据；历史承诺、网页文字或旧任务不能自动授予新行动权限 |
| 自动周报“编出”因果或成长 | 将事件、模型解释与用户评价分开；允许展示未决和矛盾 |
| 错误经验越来越常被引用 | 版本管理、反例回写、失效处理、避免派生总结被当成独立新证据 |
| 服务退出导致个人记忆不可用 | 开放导出，保留来源和关系，提供离线可读形式；迁移不能只导出无上下文摘要 |

Windows Recall 当前公开说明包括主动开启、暂停、应用／网站过滤、删除、本地处理和身份验证；文档也提示某些过滤场景有边界。因此“给一个隐私开关”不够，范围与例外都要能被用户理解。[Microsoft 官方说明](https://support.microsoft.com/en-us/windows/privacy/privacy-and-control-over-your-recall-experience)

Limitless 官方公告明确 Rewind 停止采集等变化，并提供导出和删除安排。这说明长期个人记忆需要考虑产品生命周期；不能由这次服务变化反推整个记忆方向没有市场。[Limitless 官方公告](https://www.limitless.ai/)

关于生成式系统影响人的回忆，一项证人访谈实验发现特定聊天机器人条件增加了错误记忆。其情境不能直接推广为普通工作助手的风险概率，但足以支持审慎设计：生成叙述不能冒充事实记录。[原始研究](https://arxiv.org/abs/2408.04681)

原讨论中几个机制需要调整：复制、粘贴、继续追问只能作为使用线索；继续追问也可能是没解决。未打开不能直接解释为失败，24 小时不应导致经验枯萎。结果质量的不稳定也不适合包装成抽卡；惊喜可以来自意外发现了相关旧材料，而任务质量仍须稳定。把这些行为称为“同一个神经回路”缺乏本轮可核查证据，不作为产品依据。

## 10. MVP：围绕一个真实项目检验跨任务收益

首批候选用户是已有高频 AI 使用、跨应用工作、项目持续数周且会重复解释背景的人，例如产品、研究、设计或咨询工作者。先选其中一个群体；不是因为模型只能处理这一行业，而是便于观察相同的问题。不同群体的资料权限和任务风险差别很大。

最小范围建议：一个桌面平台、一个轻量入口、一个主要工作来源和一个项目。保留用户已有 AI 工具；在可授权读取或显式导入的范围内消费它们的产物。不要假定所有产品都能稳定导出完整聊天。

第一版包含六项能力：

1. 在当前应用明确召唤，读取选区、指定窗口或用户分享的内容，并就地回答。
2. 任务后生成带来源的问题案例；当前无结果证据时如实标注。
3. 从案例中抽取少量决策和方法候选，自动去重并关联项目。
4. 新任务中检索相关案例，显示来源和为何相关，直接协助产出。
5. 用户随时纠正、撤回、忽略历史、删除和导出；更正影响下一次调用。
6. 一个简洁“书架”视图，展示少量真实案例及其复用／修订过程。

MVP 不需要完整农场、皮肤商店、三维场景、全时录屏、完整个人画像或全面自动执行。长任务可以复用现有运行框架，进度状态与记忆资产各自保存，避免为了提供收获而人为延长任务。

方案也兼容当前只读助手：帮助用户做判断、生成草稿、提取方法就可测试价值。执行类技能、主动改文件和外发消息，应在相应能力和授权边界成熟后扩展。

## 11. 验证方案：把“有记忆”“有空间”“能留存”拆开

以下人数与门槛是建议的试验设计，非行业标准，也不是已有结果。先用小样本找失败模式，再根据效应和方差规划更大样本。

### A. 问题验证与短期试用

先访谈并观察 8–12 名目标用户，追溯过去两周实际发生的“重新解释、重找材料、重复踩坑”，而不是问是否喜欢博物馆。选出有重复任务者，试用 2–3 周。记录没有复用机会的用户及原因，避免只看成功者。

每位用户可自选一个项目和 3–5 段历史案例作为起点。首日目标是理解来源与控制方式；七天内观察是否发生首次真实复用，而不是要求固定次数的打开。

### B. 验证记忆是否改善工作

用同样的模型、当前材料和执行能力比较三种方案：只有当前上下文；可检索原始聊天／笔记；可检索结构化案例与带条件的经验。后两者的差异才说明额外整理是否值得。

离线回放按时间切分，只允许用任务发生前已存在的内容，避免把未来答案写入历史。覆盖精确找回、模糊回忆、跨次联系、事实更新、旧知识不适用和没有证据应保持不确定等任务。对输出进行盲评；在线测试再观察真实操作收益与打扰。

LongMemEval 将信息抽取、跨会话推理、时间推理、知识更新和拒答纳入长期记忆评估；可借鉴其维度，但基准问答成绩不能替代本产品真实任务效果。[LongMemEval，ICLR 2025](https://arxiv.org/abs/2410.10813)

避免让同一个用户重复完成同一道题来简单计时，因为他已经学习过答案。可使用难度相当的匹配任务、随机顺序或不同用户，并报告任务难度和记忆可用性差异。基线也应允许正常搜索，不能故意削弱。

### C. 验证空间是否有独立价值

固定同一批经验、同一记忆能力和提醒频率，比较普通列表与轻量书房／展柜视图。测找到经验的时间、主动回顾、对来源和变化的理解、是否愿意保留、当前任务完成情况。若要比较农场，需要保证奖励与任务能力一致。

先用可交互原型做理解和偏好测试，再在真实工作中观察 4–6 周。小样本偏好不能当作长期留存结论；要留意展示顺序、新鲜感和参与研究本身造成的影响。

### D. 指标与停止条件

北极星候选是“每周被验证对当前工作有帮助的历史经验复用”，同时看有自然复用机会的活跃用户覆盖率。一次复用应能指出来源、进入的任务和帮助依据。复制、点击、打开只算代理信号，不能自动算有效复用；可少量抽样回访校准，日常不强制打分。

| 指标 | 衡量方式 | 早期参考门槛／处理 |
|---|---|---|
| 首次价值 | 第一次正确使用旧经验的时间 | 有复用机会者七天内能出现；否则先查来源与触发是否合理 |
| 任务收益 | 质量、完成时间、重复说明、返工 | 相对“原始聊天可检索”基线有实际改善；可预设时间降低约 20% 且质量不下降为探索门槛 |
| 有效复用覆盖 | 每周至少一次有依据的复用用户比例 | 试验中有机会者至少一半出现；小样本只作决策信号 |
| 维护负担 | 纠正、整理、确认耗时 | 中位数每人每周不超过约 5 分钟，且小于实际收益 |
| 召回质量 | 相关性、来源支撑、边界判断 | 分别统计误用、漏掉和合理不调用，不能只追召回率 |
| 信任 | 错误归属、过期规则、越界访问、删除后残留 | 严重越界或删除失效应立即暂停相关自动化并修复 |
| 长期回访 | 四至六周主动调用、关闭／卸载、关闭原因 | 单独区分助手调用与空间浏览，不把开机常驻算活跃 |
| 商业意愿 | 继续用的承诺、真实付费选择、替代产品 | 意向不能代替付费；记录不愿付费者为何更偏爱已有工具 |

以下结果对应不同方向：记忆有益、空间无益，则优先做轻量助手或插件；空间有情感价值、记忆无工作收益，则重新评估为个人回顾产品；两者都有效，再建设更丰富个人世界；两者都弱，则停止加功能，重选用户和任务。

原始记忆检索已经表现足够好时，不继续投入复杂知识图谱。若需要大量用户整理才出现收益，应先收窄采集与提炼范围，而不是增加提醒和打卡。

## 12. 商业与实施顺序

即时桌面帮助决定用户愿不愿意开始，跨任务收益决定记忆是否值得付费，个人空间可能增加情感价值和辨识度。它们分别对应不同证据，漂亮演示只能证明可理解和有吸引力。

先考虑软件订阅与透明用量的可行性，不依赖皮肤消费、广告或奖励 token 消耗。持续处理上下文有模型、索引、存储和支持成本；默认全量录屏、不断重新总结会同时增加成本和隐私压力。需记录每个有效复用对应的处理成本，而非只看每次回答价格。

商业化前应核对所用开源运行框架及组件的许可、模型接入条款和第三方连接的稳定性。使用成熟框架可以降低开发量，但不会自动保证跨应用权限、上下文质量、延迟、可靠性和支持成本。

推荐顺序：先把一个项目的“召唤→带来源案例→下一次复用→纠正生效”跑通；再检验轻量空间；随后才是更丰富的自动整理、回顾和主动协助。若已有工程，就增量补这一条链，不从零重建通用 Agent 平台。

仍需验证的三个问题最关键：目标人群多久遇到一次值得调用个人历史的任务；系统能否在低维护情况下正确使用并更新这些历史；空间体验能否在工作收益之外带来持久价值。现有研究与竞品能支持这些问题值得做，但不能替我们给出肯定答案。
